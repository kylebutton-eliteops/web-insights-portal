How to use the ZIA Toolkit (standalone copy)

Export, set up, analyze, read the results.

Four steps: export logs from ZIA, start the toolkit, add the export, download the CSV. The first run takes about ten minutes to set up; after that it's a couple of minutes per export.

1. Export logs from Web Insights

  1. In the ZIA admin console, open Analytics → Web Insights and switch to the Logs view. (Menu names can differ a little in the new Experience Center.)
  2. Pick the time range. Web Insights exports at most 1,000,000 rows, so for a busy tenant use a few hours to a day at a time, or add filters (location, department, policy action).
  3. Add filters if you want: for example Policy Action = Allowed to review what's getting through, or a single location or department.
  4. Open the column picker and make sure these columns are on. The toolkit skips any that are missing:
    • Required: URL
    • Recommended: Event Time, User, Policy Action, URL Category, URL Super Category, URL Class, Cloud Application, Cloud Application Class, Department, Forwarding Rule, Certificate Chain Validity, ALPN Protocol
    • For "which rule did it hit": any rule-name columns (URL Filtering rule, Cloud App Control rule, SSL Inspection rule). The toolkit picks up every column with "Rule" in its name and adds it to the output.
  5. Click Export → CSV. Don't open and re-save the file in Excel first; upload it exactly as downloaded.

2. Set up the toolkit (first time only)

  1. Install Python 3.9 or newer (python3 --version to check).
  2. Open a terminal in the zia_toolkit folder and run ./run.sh (macOS / Linux) or .\run.ps1 (Windows PowerShell). It creates a private Python environment, installs what it needs and starts the toolkit.
  3. Open http://127.0.0.1:5055. Everything runs on this one page and only listens on your own computer.
  4. Connect Zscaler once (needed for category lookups, optional for the rest). You need a OneAPI client:
    • In ZIA, create a read-only API role (view access to URL categories and URL Filtering policy).
    • In ZIdentity, go to Integration → API Resources → Sync Now, then API Clients → Add, pick Client Secret, and tick the ZIA role under Resources.
    • Either type the vanity domain (the part before .zslogin.net), client ID and secret into the dashboard (kept in memory until you stop the toolkit), or copy .env.example to .env and fill in ZIA_VANITY_DOMAIN, ZIA_CLIENT_ID, ZIA_CLIENT_SECRET and restart.
    The same connection is used by every tool. A legacy ZIA API key also works via .env (ZIA_USERNAME, ZIA_PASSWORD, ZIA_API_KEY, ZIA_CLOUD).

3. Upload and analyze

  1. On the dashboard, add the CSV you exported to the library, then open Web Insights and pick it.
  2. Leave Also look up current Zscaler categories ticked if you connected Zscaler. It adds about a minute per 5,000 new hosts; hosts already in the shared cache are skipped.
  3. Click Analyze. A 1M-row export takes about a minute without the lookup.
  4. When it finishes, download:
    • Hosts CSV: one row per host, which is usually what you want.
    • All CSVs (.zip): the hosts CSV plus category, SSL, forwarding rule and rule-name summaries.
    • Excel workbook: everything above as tabs. Import it into Google Sheets with File → Import.

Exports stay in the library (they contain user names) until you remove them on the dashboard. Everything is saved directly in the folder the toolkit runs from: exports in logs/, results in output/, and the lookup cache in lookup_cache.json.

Block impact: what breaks if we block these categories?

ZIA logs record only the one category a URL matched, but most URLs carry several. A new block rule for File Host also catches SharePoint, because SharePoint is classified as both Corporate Marketing and File Host. Block impact looks up every category for each domain in your logs and shows what a planned block would catch, before you turn it on. About 10 minutes plus lookup time.

  1. Export your logs from ZIA. In the ZIA Admin Portal, go to Analytics › Web Insights and switch to the Logs view. Set the time range (14 days is the maximum there) and filter Policy Action to Allowed. Before exporting, turn on these columns: URL, Policy Action, URL Category, User, and the rule columns (URL Filtering Rule Name, Cloud Application Policy / rule name, Blocked Policy rule name). Then export to CSV. Several files are fine. A CSV from a SIEM or ADX works too, as long as it has a URL or domain column.
  2. Add the files and do a Dry run. Add the CSVs to the library on the dashboard (or drop them in box A inside Block impact) and click Dry run. It reads the files without contacting Zscaler and shows which columns it found. Check the warnings: without a URL Category column, "Logged as" and Hidden detection won't work, and without the URL filtering rule column the tool works out the enforcing rule from your URL filtering rules instead (marked "sim").
  3. Run the lookup. Make sure Zscaler is connected (step 2), then click Run lookup. Zscaler allows 400 requests an hour at 100 domains each, so 40,000 domains an hour. Results are cached and shared with Web Insights; if you stop, running again resumes where it left off.
  4. Review the impact. On the Review impact tab, pick a saved category list (for example High-risk categories (example)) and click Evaluate list, or tick categories in the Categories menu. Read the four numbers and the Impact by blocking category table (which category on your list causes the most impact), then the domain table, where Would be blocked as shows the category each domain would be blocked under. Rows marked Hidden are the surprises: the logs filed them under a different category, so nobody would expect the block to hit them. Tick Exc on anything that must keep working and copy the list into a custom URL category or an allow rule above the new block.

Everything runs on this computer. Log files, cached lookups and results are kept in /tmp/ztw5, and nothing is sent anywhere except the domain names to Zscaler's own URL lookup API. Hover over any ? or button in Block impact for help. Its original guide is in category_impact/README.txt.

Troubleshooting

  • "Couldn't find a header row with a URL column": the file isn't a Web Insights CSV, or the URL column was turned off before exporting.
  • Exactly 1,000,000 rows: you hit the export limit. Export shorter time ranges and run each one.
  • "OneAPI sign-in failed (HTTP 401)": check the client ID and secret, and that the vanity domain is only the prefix (e.g. acme, not https://acme.zslogin.net).
  • "Can't reach …zslogin.net": your network or proxy is blocking it. Try off-VPN, or skip the lookup.
  • Lookup errors with HTTP 403: the API client's ZIA role is missing URL lookup access.
  • Port 5055 already in use: start it with PORT=5056 ./run.sh.
  • Upload fails for very large files: the limit is 2 GB. Split the time range.
